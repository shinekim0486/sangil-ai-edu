## 1. 이 과목이 자율주행차에서 만드는 것

자율주행차가 트랙에서 무엇을 인식하지 못하는지를 문제로 정의하고, 정지선·표지판·장애물 인식 모델을 골라 학습시킨다.

## 2. 최종 도달점 — 완성 판정 기준

- [ ] 차가 트랙에서 무엇을 인식하지 못하는지 문제로 적혀 있다
- [ ] 목표가 숫자로 정해져 있다 (예: 정지선 인식률 90퍼센트 이상)
- [ ] 입력·출력과 제약(추론 속도, 메모리)이 요구 사항으로 명세되어 있다
- [ ] 후보 모델을 두 개 이상 비교한 표가 있다
- [ ] 학습 데이터와 검증 데이터가 나뉘어 있다
- [ ] 인자를 어떻게 바꿨고 성능이 어떻게 변했는지 기록이 있다
- [ ] 목표 성능이 나오고 왜 그 성능인지 설명할 수 있다
- [ ] 추론 시간이 실시간 제약 안에 들어온다

## 3. 단계별 경로

| 단계 | 해야 할 것 | 완료 판정 | 자주 막히는 지점 |
|---|---|---|---|
| 1. 목표 설정 | 트랙에서 차가 무엇을 못 봐서 문제가 났는지 장면으로 식별하고 해결 목표를 숫자로 정한다 | 목표가 숫자로 적혀 있다 | "잘 되게 한다" 같은 목표 |
| 2. 요구 사항 정의 | 입력과 출력, 제약(몇 밀리초 안에 판단해야 하는지)을 명세한다 | 명세서가 있다 | 실시간 제약을 빼먹고 큰 모델을 고름 |
| 3. 후보 모델 도출 | 규칙 기반 영상 처리, 소형 분류 모델, 경량 객체 탐지를 비교한다 | 비교표가 있다 | 무조건 딥러닝부터 고름 |
| 4. 알고리즘 선정 | 후보의 특성을 분석해 하나를 고르고 근거를 남긴다 | 선정 근거가 있다 | 근거 없이 유명한 것을 고름 |
| 5. 학습 모델 준비 | 시뮬레이터 데이터와 실차 촬영분을 모아 학습용과 검증용을 나눈다 | 나뉘어 있다 | 안 나눠서 성능이 실제보다 좋게 나옴 |
| 6. 인자 조율 | 학습률·배치 크기·에폭을 한 번에 하나씩 바꾸며 기록한다 | 조정 이력 표가 있다 | 여러 개를 한꺼번에 바꿔 원인을 못 찾음 |
| 7. 학습 수행·검증 | 학습을 돌리고 검증 데이터로 성능을 확인한다 | 목표 성능을 달성하고 근거를 설명할 수 있다 | 학습 데이터 성능만 보고 끝냄 |

> 실제 트랙 사진이 아니라 규격대로 그린 장면으로 잰 값이다. 실제 조명에서는 달라질 수 있다.

| | 규칙 기반 | 작은 신경망 |
|---|---|---|
| 정확도 | **99.0 %** (오탐 1건) | 100 % |
| 추론 시간 | 0.289 ms | 0.016 ms |
| 데이터 | 필요 없음 | 480장 |
| 왜 그렇게 판단했는지 설명 | **가능** | 어려움 |

**정지선 인식은 규칙 기반으로 충분하다.** 딥러닝을 먼저 꺼내지 마라.

**거리에 따른 인식률** — 멀면 못 보지만 다가가면 반드시 본다.

| 정지선까지 | 인식률 |
|---|---|
| 37 cm | 0 % |
| 33 cm | 17 % |
| 29 cm | 83 % |
| **25 cm 이하** | **100 %** |

**제동 계산 (실측 기준)** — 인식 0.3 + 통신 50 + 제동 100 = 150 ms.
0.25 m/s에서 **3.8 cm** 진행한다. 25 cm 앞에서 보므로 여유가 20 cm 넘게 남는다.

**규칙 기반이 어떻게 찾는가**
1. 흑백으로 바꾼다
2. 밝은 부분만 남긴다 — **고정 임계값(예: 200)을 쓰지 마라.** 어두운 조명에서 전부 놓친다.
   상위 15 %를 흰색으로 보는 방식(백분위수)이면 조명이 바뀌어도 따라간다
3. 가로줄마다 흰 화소 비율을 센다. 정지선은 가로로 길고, 차선은 세로라 조금만 걸린다
4. 비율이 0.32를 넘는 줄이 있으면 정지선이다

**파라미터는 재서 정한다** — 감으로 잡은 값 78.8 % → 36가지 조합을 돌려 92.6 %.

**후보 모델 비교 — 규칙 기반을 반드시 후보에 넣는다**

| 후보 | 장점 | 단점 | 언제 유리한가 |
|---|---|---|---|
| 규칙 기반 영상 처리 (색 범위 + 직선 검출) | 매우 빠르고 데이터가 필요 없다. 왜 그렇게 판단했는지 설명할 수 있다 | 조명이 바뀌면 약하다 | 정지선·차선처럼 색과 모양이 뚜렷할 때 |
| 소형 분류 모델 | 조명 변화에 강하다 | 데이터가 필요하다 | 표지판 종류를 구분할 때 |
| 경량 객체 탐지 | 무엇이 어디에 있는지까지 알려 준다 | 무겁고 느리다 | 장애물 위치가 필요할 때 |

정지선은 규칙 기반이 더 빠르고 정확한 경우가 많다. 딥러닝이 항상 정답은 아니라는 것을 비교표로 직접 확인하는 것이 이 단계의 핵심이다.

**데이터 분리** — 학습과 검증을 8 대 2로 나눈다. 시험용까지 두면 7 대 2 대 1로 나눈다.

- 같은 주행 영상에서 뽑은 연속 프레임을 학습과 검증에 나눠 넣으면 안 된다. 거의 같은 그림이라 성능이 부풀려진다. 주행 회차 단위로 나눈다

**과적합 판별**

| 학습 정확도 | 검증 정확도 | 해석 |
|---|---|---|
| 높음 | 높음 | 정상 |
| 높음 | 낮음 | 과적합. 데이터를 늘리거나 모델을 줄인다 |
| 낮음 | 낮음 | 학습 부족. 에폭과 학습률을 조정한다 |

**인자 조율 기록표** — 회차 / 바꾼 인자 / 값 / 학습 정확도 / 검증 정확도 / 메모. 한 번에 하나만 바꾼다.

**실시간 제약 계산** — 차가 초당 30 센티미터로 달리고 판단에 0.2초가 걸리면, 판단하는 동안 6 센티미터를 더 간다. 정지선 앞에 서려면 이 거리를 빼고 미리 멈춰야 한다. 한 장 판단하는 데 걸리는 시간을 반드시 잰다.

**조향 모델 — 화면을 보고 조향을 직접 낸다**

정지선 인식은 규칙 기반으로 충분하지만, **조향은 학습이 필요하다.**
사람(또는 잘 도는 제어기)이 운전하는 걸 신경망이 흉내 내게 한다.
행동 복제(behavior cloning)라고 한다.

실제로 만들어 확정한 구조다.

| 층 | 하는 일 | 출력 | 파라미터 |
|---|---|---|---|
| 입력 | 흑백 화면 | 1 × 96 × 128 | — |
| 합성곱 1 | 5×5 보폭 2 | 12 × 48 × 64 | 312 |
| 합성곱 2 | 5×5 보폭 2 | 24 × 24 × 32 | 7,224 |
| 합성곱 3 | 3×3 보폭 2 | 36 × 12 × 16 | 7,812 |
| 합성곱 4 | 3×3 보폭 2 | 48 × 6 × 8 | 15,600 |
| 전결합 1 | 2304 → 64 | 64 | 147,520 |
| 전결합 2 | 64 → 2, tanh | 조향 · 속도 | 130 |
| **합계** | | | **178,598개 · 698 KB** |

출력이 **둘**이다. 조향만 내면 차가 신호등과 표지판을 보고도 속도를 못 바꾼다.
속도는 0~1 이고 목표 속도(0.25 m/s)를 곱해서 쓴다. 빨간불 앞에서는 0 이 된다.

**왜 아두이노가 아니라 라즈베리파이인가**

한 장 판단에 **곱셈 884만 회**가 필요하다. 초당 20장이면 1억 7,700만 회/초다.

| 장치 | 연산 | 메모리 | 판정 |
|---|---|---|---|
| 아두이노 우노 | 50만 회/초 | **2 KB** | 불가 — 이미지 3 KB 도 못 올린다 |
| ESP32-CAM | 1억 회/초 | 4 MB | 빠듯 |
| **라즈베리파이 4** | 80억 회/초 | 4 GB | **가능** |

과거 PC 참고 구현에서는 ONNX Runtime으로 초당 9,418장을 측정했다.
파이 초당 1,177장은 PC 값을 비율로 환산한 **예상치이며 실차 측정이 아니다.**
실시간 동작 여부는 실제 파이에서 카메라·모델·제어 판단·통신의 전체 지연을 재서 판단한다.

**학습·검증을 어떻게 나누나**

장 단위로 섞어 나누면 **바로 옆 프레임이 검증에 들어가** 성능이 부풀려진다.
**주행 회차 단위**로 갈라야 한다. 정방향으로 배우고 역방향으로 검증하면
외운 것인지 도로를 본 것인지 가려진다.

실측 — 학습에 한 장도 안 쓴 역방향 6,000장에서 **좌우 방향 일치율 90.2 %**.

**데이터가 쏠리면 못 배운다**

원형 트랙에서 모았더니 직진 66.8 %, 우회전 0장이었다.
코스를 바꾸고 양방향으로 모아 좌우 불균형을 1.02배로 맞췄다.
학습할 때 두 가지를 더 한다.

- **좌우 반전 증강** — 이미지를 뒤집고 조향 부호를 바꾼다. 데이터가 두 배가 된다
- **쏠림 덜어내기** — 직진이 너무 많으면 잘라낸다. 안 하면 "웬만하면 직진"만 배운다

**라즈베리파이로 옮기기 — 모델과 입력 계약을 확인한다**

학습은 PC에서 PyTorch로 하고 ONNX로 내보낸다. **파이에서는 해당 모델의 입출력과 전처리가 실행 코드에 맞는지 먼저 확인한다.**
유니티가 만든 파일이 아니므로 별도 변환이 필요 없다.

    # PC — 학습이 끝나면
    torch.onnx.export(model, (dummy,), "drive_model.onnx",
                      input_names=["image"], output_names=["steer"],
                      dynamic_axes={"image": {0: "batch"}})

    # 라즈베리파이 — onnxruntime 만 설치하면 된다
    pip install onnxruntime
    import onnxruntime as ort
    sess = ort.InferenceSession("drive_model.onnx")
    steer = sess.run(None, {"image": img})[0][0][0]

**옮길 때 맞춰야 할 것 세 가지**

파일은 그대로 쓰지만, 입력을 학습 때와 똑같이 만들어야 한다. 여기가 어긋나면 안 된다.

| 항목 | 맞춰야 할 값 |
|---|---|
| **화면 크기** | 파이 카메라가 무엇을 찍든 **128 × 96 으로 줄인다** (가로 128 · 세로 96 · 흑백 1채널 · 출력 2개 조향·속도). 64 × 48 은 8/27 이전 옛 모델 값이다 |
| **카메라 화각** | 유니티 `fieldOfView 41` = 수평 53° × 수직 41°. 실제 카메라(Module 3 표준)와 반드시 같아야 한다 |
| **흑백 변환** | 0.299 R + 0.587 G + 0.114 B — 학습 때와 같은 식 |
| **밝기 범위** | 0 ~ 255 를 **0 ~ 1 로 나눈다** |
| 위아래 방향 | 화면 맨 윗줄이 배열의 첫 줄이어야 한다 |

**시뮬레이터에서 되는데 실차에서 안 되는 이유**

같은 모델인데 결과가 다르면 대개 아래 중 하나다.

- 시뮬레이터에 있는 물체가 실물에 없다(또는 반대). 가드레일을 넣었다가 뺀 이유가 이것이다
- 노면·잔디 색이 다르다. 시뮬레이터 색을 실제 트랙에 맞춰야 한다
- **카메라 화각이 다르다.** 실제 카메라(Camera Module 3 표준)는 센서가 16:9 라 수평 66°×수직 41° 지만,
  학습 입력인 128×96(4:3)로 자르면 **수평 53°×수직 41°** 가 된다.
  유니티는 `fieldOfView = 41`(수직 기준)로 맞춘다. 이 둘이 어긋나면 모델이 전혀 다르게 움직인다
- 조명이 다르다. 여러 조명 조건으로 데이터를 모아 둔다

### 교사 실차 경험의 적용 범위

2026년 10월 교사 시제품의 관찰을 익명화한 진단 사례다. 학생 팀의 성공이나 모든 장비의 표준값을 뜻하지 않는다. 수업 표준과 승인된 팀 규격을 보존하고, 완성본 소스·모델·교사 원본 기록은 공개하지 않는다.

### 교사 실차 사례 — 요청한 카메라 영역과 실제 영역을 구분한다.

카메라 설정을 요청했어도 센서 모드에 따라 실제 잘린 영역이 달랐던 교사 사례가 있다. 요청값과 실제 메타데이터, 저장된 모델 입력 화면을 대조한다. 학습 당시 입력 영역을 목표로 정했다면, 그 영역을 제공할 수 있는 센서 모드를 검토한다. 단순히 요청값을 현재 센서의 작은 최대 영역에 맞춰 줄여 놓고 학습 입력과 일치한다고 처리하지 않는다. 해상도만 같다고 화각·회전·흑백 변환까지 같다고 판단하지 않는다. 학생 장비를 확인하기 전에 교사 장비의 설정값을 복사하지 않는다.

### 교사 실차 사례 — 저장·모델 검사·실차 완주의 증거를 나눈다.

설치 성공, 저장 완료, 정지 상태의 방향 출력, 기록 재검사, 실제 완주는 서로 다른 확인이다. 카메라 입력이 일치해도 실차 주행 검증은 남는다. 시뮬레이터 완주만으로 실제 자동차 주행 검증이 끝났다고 말하지 않는다. 같은 주행의 인접 사진을 섞으면 검증 결과가 부풀려진다. 교사의 네 시도 중 하나씩 뺀 검사는 같은 코스의 개발 검증이며 독립된 새 환경 시험이 아니다. 한 바퀴 완주는 1회 주행 관찰이며 전체 검증 종료를 뜻하지 않는다. 반복 안정성과 바퀴 경계 준수는 따로 기록한다.

## 6. 다른 과목과의 접점

**받는 것**
  - 시뮬레이터와 합성 학습 데이터 ← 게임 프로그래밍
**주는 것**
  - 학습된 인식 모델 → 네트워크 프로그래밍

범위 밖 질문이 오면 담당 과목을 알려 주고 그 팀에 요청하라고 안내한다.
