## 1. 이 과목이 자율주행차에서 만드는 것

자율주행차 관제 화면의 UX 설계와 UI 디자인. 주행을 지켜보는 화면에 무엇을 어떻게 보여줄지 정보 구조를 짜고, 와이어프레임과 스토리보드를 그리고, 스타일 가이드와 시안을 만들어 구현 팀에 넘긴다. **코딩은 하지 않는다. 설계와 디자인까지가 이 과목의 몫이다.**

## 2. 최종 도달점 — 완성 판정 기준

- [ ] 관제 화면의 정보 구조도가 있다
- [ ] 화면마다 와이어프레임이 있다
- [ ] 스토리보드에 화면 전환과 조건이 적혀 있다
- [ ] 워크플로우가 막혔을 때의 분기까지 포함해 그려져 있다
- [ ] 내비게이션 구조가 정의되어 있다
- [ ] 디자인 콘셉트 문서가 있다
- [ ] 스타일 가이드에 색·글꼴·버튼·표·차트 규칙이 있다
- [ ] 시안이 있고 구현 팀이 그것만 보고 만들 수 있다

## 3. 단계별 경로

| 단계 | 해야 할 것 | 완료 판정 | 자주 막히는 지점 |
|---|---|---|---|
| 1. 정보 구조 설계 | 관제 화면에 무엇을 보여줄지 정하고 중요도에 따라 계층으로 묶는다 | 정보 구조도가 있다 | 어떤 데이터가 오는지 안 정하고 그림부터 그림 |
| 2. 와이어프레임 | 화면별로 요소를 어디에 둘지 배치한다. 색은 아직 쓰지 않는다 | 화면 수만큼 와이어프레임이 있다 | 처음부터 예쁘게 꾸미다 배치를 못 정함 |
| 3. 스토리보드 | 화면이 언제 어떻게 바뀌는지 조건과 함께 적는다 | 흐름이 끊기지 않고 이어진다 | 정상 흐름만 그리고 예외 상황을 빠뜨림 |
| 4. 워크플로우 | 사용자가 막혔을 때 어디로 가는지 분기를 그린다 | 막다른 화면이 없다 | 되돌아갈 길을 안 그림 |
| 5. 내비게이션 설계 | 화면 사이를 어떻게 오갈지 정한다 | 어느 화면에서든 현재 위치를 알 수 있다 | 깊이가 너무 깊어 헤맴 |
| 6. 디자인 콘셉트 수립 | 이 화면이 어떤 인상이어야 하는지 정하고 근거를 적는다 | 콘셉트 문서가 있다 | 취향으로만 정함 |
| 7. 스타일 가이드 제작 | 색·글꼴·버튼·표·차트 규칙을 정리한다 | 다른 사람이 그대로 따라 만들 수 있다 | 시안만 주고 가이드를 안 만듦 |
| 8. 시안 제작·검토 | 최종 시안을 만들고 구현 팀과 검토해 의견을 반영한다 | 구현 팀이 합의한 시안이 있다 | 혼자 만들고 통보함 |

## 4. 검증된 예시 코드·자료

**반드시 지킬 것** — 아래는 팀마다 바꾸지 않는다. 다르게 하면 틀린 것이다.

| 항목 | 값 |
|---|---|
| 뜻을 가진 색 | **4개 이내** — 먹·회·강조·경고. 각각 언제 쓰는지 적는다 |
| 바탕·선·머리행 | 뜻이 없으므로 **따로 센다.** 이걸 섞어 세면 규칙을 못 지킨다 |
| 그래프 기준선 | **250mm 정지선 인식 거리**를 반드시 넣는다. 숫자만 보면 판단이 안 된다 |
| 표시할 항목 | 네트워크 팀 패킷 6개 — 순번·시각·앞거리·조도 좌우·속도·지연 |
| 글꼴 종류 | **2종 이내** |
| 상태 구분 | **색만으로 구분하지 않는다** — 글자나 모양을 같이 쓴다 |
| 구현 팀에 넘길 것 | 시안 **+ 스타일 가이드**. 시안만 주지 않는다 |
| 표시할 데이터 | **네트워크 팀 패킷 포맷 문서를 먼저 받고** 정한다 |
| 주행 로그가 어디서 오나 · 로그 출처 | **라즈베리파이**가 카메라를 보고 조향을 정한 뒤 아두이노에 보낸다. 그 기록이 관제로 올라온다 |
| 새로 보여줘야 할 것 | **모델이 낸 조향값**(−1 ~ +1)과 조도 센서 값을 같이 본다. 둘이 다르면 모델이 뭘 봤는지 알 수 있다 |
| 트랙 규격 · 코스가 몇 미터 | 트랙 **3600 × 2400 mm** · 주행로 **300 mm** · 한 바퀴 **11.14 m** |
| 이탈 표시 기준 | 중심선 이탈 **85 mm** 를 넘으면 바퀴가 차선을 밟는다. 그 선을 그래프에 넣는다 |

**관제 화면에 반드시 들어갈 데이터** — 네트워크 팀 패킷에서 오는 값이다. 설계 전에 그 문서를 먼저 받는다.

| 항목 | 성격 | 어떻게 보여줄까 |
|---|---|---|
| 측정 시각 | 시간 | 표의 첫 열 |
| 앞 거리 (초음파) | 숫자, 계속 변함 | 큰 숫자 + 선그래프 |
| 밝기 (조도) | 숫자 | 선그래프 |
| 속도·명령 | 상태 | 아이콘 또는 색 |
| 통신 지연 | 숫자, 이상 감지용 | 기준선이 있는 선그래프 |

**색 쓰는 규칙**

- 색은 꾸미는 데 쓰지 않고 상태를 구분하는 데 쓴다. 정상·주의·위험 세 가지면 충분하다
- 전체 색은 다섯 개 이내로 제한한다. 늘어날수록 무엇이 중요한지 알 수 없게 된다
- 색만으로 구분하지 않는다. 색을 못 보는 사람도 있으므로 글자나 모양을 같이 쓴다

**표현 방식 고르기** — 지금 값 하나는 큰 숫자로, 시간에 따른 변화는 선그래프로, 여러 항목 비교는 막대로, 기록 목록은 표로 한다.

**스타일 가이드 최소 항목** — 색 다섯 개 이내(각각 언제 쓰는지 명시), 글꼴 두 종 이내, 버튼 네 가지 상태(기본·마우스 올림·눌림·비활성), 표와 차트 규칙, 여백 기준.

**도구** — Figma 무료 계정이면 충분하다. 파워포인트로도 와이어프레임과 스토리보드는 만들 수 있다.

## 5. 자주 나오는 질문과 되물어야 할 것

| 학생이 이렇게 물으면 | 이렇게 되묻는다 |
|---|---|
| 뭘 그려야 해요? | 이 화면을 누가 언제 봐? 보고 나서 뭘 해야 해? |
| 예쁘게 안 나와요 | 지금 색이 몇 개야? 글꼴은 몇 종이야? 줄여 보는 건 어때? |
| 구현 팀이 다르게 만들었어요 | 스타일 가이드를 줬어? 거기에 그 부분이 적혀 있었어? |
| 어떤 데이터가 오는지 몰라요 | 네트워크 팀 패킷 포맷 문서 받았어? 안 받았으면 그것부터 요청하자 |
| 차트를 어떻게 골라요? | 그 값이 시간에 따라 변하는 거야, 지금 값 하나야? |
| 다 만들었어요 | 구현 팀이 이것만 보고 만들 수 있을까? 색 코드랑 글자 크기가 적혀 있어? |

## 6. 다른 과목과의 접점

**받는 것**
  - 화면에 표시할 데이터 항목(패킷 포맷) ← 네트워크 프로그래밍
**주는 것**
  - 스타일 가이드와 시안 디자인 → 응용 프로그래밍 개발 — 화면

범위 밖 질문이 오면 담당 과목을 알려 주고 그 팀에 요청하라고 안내한다.
