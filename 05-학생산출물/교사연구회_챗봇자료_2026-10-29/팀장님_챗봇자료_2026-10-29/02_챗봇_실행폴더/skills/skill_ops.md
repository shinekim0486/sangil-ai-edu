## 1. 이 과목이 자율주행차에서 만드는 것

학급 전체가 쓰는 챗봇 서버의 운영. 다른 여섯 과목 학생 전원이 매일 이 서버에 접속한다. 서버를 설치하고 환경을 구성하고, 토큰 사용량과 응답 시간의 성능 기준을 정해 운용하고, API 키 노출을 점검하고, 장애가 나면 원인을 찾아 처리한다. 4주차부터는 응용 프로그래밍 팀이 만든 관제 서버도 함께 운영한다.

**토큰은 곧 예산이다.** 목적 없는 질문이 쌓이면 그만큼 돈이 새고, 예산이 바닥나면 다른 과목 수업이 멈춘다. 낭비를 막는 것이 이 과목의 핵심이다.

> 이 단계는 1주차부터 6주차까지 계속된다. 끝나는 단계가 아니다.

## 2. 최종 도달점 — 완성 판정 기준

- [ ] 챗봇 서버가 설치·구성되어 학급 전원이 접속된다
- [ ] 토큰 예산과 팀별·학생별 사용 상한이 정해져 있고 그 근거가 적혀 있다
- [ ] 사용량과 응답 시간을 언제든 확인할 수 있다
- [ ] API 키가 코드 안에 없고 환경 변수로 관리된다
- [ ] 낭비 패턴을 로그에서 찾아 대책을 적용하고 효과를 측정한 기록이 있다
- [ ] 장애 대장에 발생·원인·조치·재발 방지가 적혀 있다
- [ ] 6주 동안 예산 안에서 서버가 살아 있었다
- [ ] 관제 서버도 인수해 배포·운영했다

## 3. 단계별 경로

| 단계 | 해야 할 것 | 완료 판정 | 자주 막히는 지점 |
|---|---|---|---|
| 1. 서버 설치·환경 구성 | 실행 환경을 갖추고 포트와 환경 변수를 설정해 띄운다 | 다른 학생이 자기 PC에서 접속된다 | 포트가 이미 쓰이고 있음 / 키를 코드에 그대로 넣음 |
| 2. 성능 기준 수립 | 총 예산, 학생·팀 사용 상한, 목표 응답 시간을 근거와 함께 정한다 | 숫자와 근거가 문서에 있다 | 근거 없이 숫자만 적음 |
| 3. 사용량 감시 | 사용량과 응답 시간을 주기적으로 확인하고 추이를 기록한다 | 주차별 추이표가 있다 | 쌓기만 하고 안 봄 |
| 4. 보안 점검 | 키가 노출되지 않는지, 접근 권한이 맞는지 점검한다 | 점검표가 있고 통과한다 | 저장소에 키를 그대로 올림 |
| 5. 낭비 분석·대책 | 누가 언제 어떤 질문으로 많이 썼는지 찾아 대책을 세우고, 적용 후 다시 잰다 | 적용 전후 비교표가 있다 | 대책만 세우고 효과를 안 잼 |
| 6. 사용자 지원 | 다른 과목 학생 문의를 접수해 처리하고 기록한다 | 문의·처리 기록이 있다 | 구두로만 처리하고 안 남김 |
| 7. 장애 처리 | 장애를 찾아내고 종류를 나누고 복구한 뒤 기록한다 | 장애 대장이 있다 | 고치고 끝냄, 재발 방지가 없음 |
| 8. 관제 서버 운영 | 응용 프로그래밍 팀에게 인수해 배포하고 같이 지켜본다 | 관제 화면이 수업 시간에 계속 열린다 | 인수인계 문서 없이 받음 |

## 4. 검증된 예시 코드·자료

**반드시 지킬 것** — 아래는 학생이 임의로 바꾸지 않는다. 바꾸려면 근거와 기록을 남긴다.

| 항목 | 값 |
|---|---|
| API 키 | **환경 변수(.env)에만 둔다.** 코드·문서·저장소에 절대 적지 않는다 |
| 키가 한 번 노출되면 | 지워도 기록에 남는다. **반드시 새로 발급**받는다 |
| 상한을 바꿀 때 | **근거 숫자와 함께 기록**한다. 감으로 바꾸지 않는다 |
| 대책을 세웠으면 | **적용 후 효과를 다시 잰다.** 세우기만 하고 끝내지 않는다 |
| 장애가 나면 | 발생시각·증상·**영향 범위(몇 명이 못 썼나)**·원인·조치·재발방지를 모두 적는다 |
| 운영 대상이 둘이다 | **챗봇 서버**와 **차량 라즈베리파이 6대**. 둘 다 우리 몫이다 |
| 파이에 올리는 것 | 교사가 승인한 팀 버전의 **모델 파일과 실행 스크립트**다. 모델 크기·입출력·필요 패키지는 버전에 따라 확인한다. 카메라 라이브러리 설치 방식과 실제 Python 환경을 먼저 확인하고 일괄 재설치하지 않는다. |
| 올리기 전에 | `08_pi_주행/selftest.py` 를 먼저 돌린다. 모델·카메라·시리얼·아두이노를 따로 본다. "차가 안 가요"로는 못 고친다 |
| 모터 핀 | 우노 PWM은 3·5·6·9·10·11 뿐이다. 9·10은 초음파가 쓰므로 모터는 **3·5·6·11**. 4·7번에 analogWrite 하면 그냥 LOW가 되어 바퀴가 아예 안 돈다 |
| 파이 SD카드 · 6개 다 따로 만들어야 하나요 · 복제 | 한 장을 만들어 **복제**한다. 팀 번호만 팀마다 다르게 넣는다 |
| 파이 전원 | 모터와 **분리**한다. 같이 쓰면 모터 기동에 파이가 재부팅된다 |
| 파이가 꺼지면 | SD카드 손상이 흔하다. **이미지를 백업**해 두고 예비 카드를 준비한다 |

**확인하는 곳**

- 사용량 보기 — 서버 주소 뒤에 `/api/usage`
- 기록 내려받기 — 서버 주소 뒤에 `/admin/export?key=관리자키` (엑셀로 열리는 CSV)
- 서버 상태 — 서버 주소 뒤에 `/healthz`

**예산 계산 방법**

    예상 비용 = 총 대화 턴 수 × (턴당 입력 토큰 + 턴당 출력 토큰) × 단가

턴당 입력은 약 2,100 토큰으로 잡는다. 출력은 단계마다 다르므로 위 상한값을 쓴다.
학생 34명이 18일 동안 하루 10턴을 쓰면 약 6,120턴이다. 여기에 여유분 20퍼센트를 더해 예산을 잡는다.

**API 키 관리**

- 키는 `.env` 파일이나 환경 변수에 둔다. 코드나 문서에 절대 적지 않는다
- `.gitignore` 에 `.env` 가 들어 있는지 확인한다. 한 번 올라간 키는 지워도 기록에 남으므로 새로 발급받아야 한다

**장애 대장 항목** — 발생 시각 / 증상 / 영향 범위(몇 명이 못 썼나) / 원인 / 조치 / 재발 방지.

### 교사 실차 경험의 적용 범위

2026년 10월 교사 시제품의 관찰을 익명화한 진단 사례다. 학생 팀의 성공이나 모든 장비의 표준값을 뜻하지 않는다. 수업 표준과 승인된 팀 규격을 보존하고, 완성본 소스·모델·교사 원본 기록은 공개하지 않는다.

### 교사 실차 사례 — 실행 중인 Python 환경을 먼저 확인한다.

교사 실차에서 같은 장치라도 다른 Python으로 실행하면 onnxruntime을 찾지 못했다. 패키지가 없다는 메시지만 보고 전체를 다시 설치하지 않는다. 실제 실행 파일·가상환경·현재 작업 폴더를 확인한다. 모듈 오류 해결과 모터 주행 검증은 구분한다. 다른 PC에 있는 파일이나 예전 IP가 현재 장치에 있다고 가정하지 않는다.

### 교사 실차 사례 — 정지 이유를 확인한 뒤 다음 검사를 정한다.

TIME_LIMIT은 설정 시간 종료, ROAD_LOST는 해당 버전의 도로 판정에 의한 정지, TURN_NO_VISIBLE_MOTION은 화면 변화 기준 미충족이었다. 모두 배터리 방전이나 코너 인식 실패를 뜻하지 않는다. 실행 버전·마지막 정지 이유·직전 명령 몇 줄만 먼저 확인한다. 버전마다 조건이 달라 실제 바퀴 동작·장면과 대조해야 한다.

### 교사 실차 사례 — 전체 제어 지연을 나누어 측정한다.

교사 파이 진단에서는 카메라·모델보다 도로 판단이 많은 시간을 썼다. 추론이 빠르다는 이유만으로 전체 제어가 빠르다고 판단하지 않는다. 카메라·모델·판단·저장·통신의 중앙값과 최댓값을 나누어 기록한다. 지연 원인을 확인하기 전에 정지 시간 제한부터 풀지 않는다. 이 결과는 그 장비의 기록이며 학생 팀의 측정값이 아니다.

## 6. 다른 과목과의 접점

**받는 것**
  - 챗봇 서버와 API 키 ← 선생님 (연구회에서 제작)
  - 배포할 관제 서버와 실행 방법 ← 응용 프로그래밍 개발 — 서버
**주는 것**
  - 서버 환경과 배포 절차 → 응용 프로그래밍 개발 — 서버
  - 사용량·장애 기록 → 전 과목 (수업 자료로 쓰인다)

범위 밖 질문이 오면 담당 과목을 알려 주고 그 팀에 요청하라고 안내한다.
