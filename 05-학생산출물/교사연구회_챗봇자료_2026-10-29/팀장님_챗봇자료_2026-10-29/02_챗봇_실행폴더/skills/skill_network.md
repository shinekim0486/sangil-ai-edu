## 1. 이 과목이 자율주행차에서 만드는 것

아두이노와 PC 사이의 텔레메트리 통신. 자체 패킷 포맷을 설계해 구현하고, 주행 로그를 DB에 쌓고, 영상과 긴급 정지 명령의 우선순위를 나누고, 지연·유실을 측정해 최적화한다.

## 2. 최종 도달점 — 완성 판정 기준

- [ ] 아두이노와 PC 개발 환경이 갖춰져 업로드가 된다
- [ ] 명령을 주면 차가 원하는 방향과 속도로 움직인다 (준비 단계, 평가 대상 아님)
- [ ] 세 센서 값이 안정적으로 찍히고 차선 안팎이 값으로 구분된다 (준비 단계, 평가 대상 아님)
- [ ] 패킷 포맷(헤더 · 센서 ID · 값 · 체크섬)이 문서로 정의되어 있다
- [ ] PC가 실시간으로 센서 값을 받고, PC가 보낸 명령대로 차가 움직인다
- [ ] 주행 로그가 데이터베이스에 쌓여 다음 시간에도 남아 있다
- [ ] 긴급 정지 명령이 영상보다 먼저 처리된다
- [ ] 지연과 유실을 측정한 값이 있고 개선 전후를 비교한 기록이 있다

## 4. 검증된 예시 코드·자료

**코드에서 반드시 지킬 것** — 아래 값은 팀마다 바꾸지 않는다. 다른 값으로 쓰면 틀린 것이다.

| 항목 | 값 |
|---|---|
| `Serial.begin()` | **115200** — 9600 아님 |
| 센서 값 안정화 | 5회 측정 후 **중앙값** — 평균 아님 |
| 패킷 헤더 | `AA 55` — 두 바이트다. 한 바이트로는 데이터와 헷갈린다 |
| 체크섬 | **CRC-8 (Dallas/Maxim)**. XOR은 쓰지 마라 |
| 체크섬 계산식 (CRC8 · crc8) | **0x8C 반사형** — 바이트마다 `c ^= b;` 한 뒤 8번 `c = (c & 1) ? ((c >> 1) ^ 0x8C) : (c >> 1);` (완성본 `arduino_telemetry.ino`·`packet.py`와 같은 식). 0x31을 왼쪽으로 미는 식(MSB 우선)은 값이 달라 파이와 아두이노가 안 맞는다 |
| 통신 상대 | **라즈베리파이 ↔ 아두이노**. 파이가 두뇌, 아두이노가 팔다리 |
| 연결 | **USB A-B 케이블.** GPIO 로 직접 이으면 3.3V/5V 차이로 파이가 상한다 |
| 파이쪽 포트 | `/dev/ttyACM0` (우노) · `pip install pyserial` |
| 전원 | 모터와 파이 전원을 **따로.** 같이 쓰면 모터 기동에 파이가 재부팅된다 |
| 왜 XOR이 아닌가 | 재 보니 **2비트 오류의 12%를 놓친다.** 같은 비트 위치가 짝수 번 뒤집히면 값이 그대로다 |
| CRC-8이 느리지 않은가 | 15바이트에 52us. 초당 20패킷이면 CPU **0.1%**다. 부담이 안 된다 |
| 긴급 정지 | **영상을 256바이트씩 조각내서** 큐에 넣는다. 통째로 넣으면 정지가 595ms 밀린다 |
| 패킷에 순번(SEQ) | 반드시 넣는다 — 없으면 유실률을 못 잰다. **패킷마다 1씩 올린다**(0~255 돌림). 고정값이면 의미가 없다 |
| 센서 패킷 페이로드 | **12바이트 이 순서** — 시각(4) · 앞거리(2) · 조도좌(2) · 조도우(2) · 속도(2). 전체 18바이트. 값을 1바이트로 줄이지 않는다(조도는 0~1023) |
| 아두이노 쪽 명령 수신 | 아두이노는 `Serial.available()`로 패킷을 모아 헤더·CRC를 확인한 뒤 **TYPE 0x05면 조향·속도로 `setMotor`**, 0x03이면 즉시 정지. 보내기만 하고 받는 쪽이 없으면 차는 안 움직인다 |
| 패킷 차례 | `AA 55` · TYPE · LEN · SEQ · PAYLOAD · CRC8 — **이 순서 그대로.** 센서값은 TYPE 0x01, 주행 명령은 0x02 |
| 보내는 방법 | **`Serial.write` 로 바이트 그대로.** `Serial.print` 는 글자(ASCII)라 `AA 55` 가 두 바이트가 아니라 글자 다섯 개가 된다 |
| 조향 명령 방향 | **파이 → 아두이노**. 아두이노는 센서값만 올려 보내고 조향을 스스로 정하지 않는다 |
| 주행 명령 (파이 → 아두이노) | **TYPE 0x05 패킷** — 조향(2) · 속도배율(1) · 깃발(1). 0x02 는 손으로 몰아 볼 때 쓰는 좌모터(2)·우모터(2) 직접 명령 |
| 긴급 정지 명령 | **TYPE 0x03 패킷** (페이로드 없음). 낱 바이트(0xFF 같은 것)로 보내지 않는다 — 모든 명령은 `AA 55` 패킷이다 |
| 아두이노가 명령을 못 받으면 | **기준 속도로 계속 간다.** 파이가 죽어도 차는 멈추지 않는다(P0). 앞이 막히면(150 mm) 아두이노가 스스로 선다 |
| 차선 유지 | **평소에는 파이의 주행 모델이 한다.** 조도 센서 2개는 보조·비상용 |
| 정지선·표지판·장애물 | **카메라** — 인공지능 팀이 만든 모델이 판단 |
| 카메라가 실패해도 | **조도 주행은 계속된다.** 인식이 안 돼도 멈추지 않게 짠다 |

**핀 배치 — 기준값**

> 교보재 확인 전에 정한 기준값이다. **안 정해진 값이 아니다.** 팀이 다른 핀을 쓰기로 하고 프로젝트 메모에 적지 않는 한 이 값을 그대로 쓴다. 실제 부품이 오면 담당 선생님이 확정한다.
> 팀이 다른 핀을 쓰기로 했다면 프로젝트 메모에 적어 두면 그 값이 우선한다.
> **코드에는 반드시 숫자를 넣고 바꿀 자리임을 주석으로 표시한다. 빈칸으로 두면 컴파일이 안 된다.**

| 부품 | 핀 | 비고 |
|---|---|---|
| 초음파 Trig | D9 | |
| 초음파 Echo | D10 | |
| 조도 센서(좌) | A0 | 아날로그 |
| 조도 센서(우) | A1 | 아날로그 |
| 모터 드라이버 좌 (IN1/IN2) | D4 / D5 | D5는 PWM |
| 모터 드라이버 우 (IN3/IN4) | D6 / D7 | D6은 PWM |
| 블루투스 RX / TX | D2 / D3 | SoftwareSerial |

```
const int trigPin = 9;    // <-- 우리 팀 핀 번호로 바꿀 것
const int echoPin = 10;   // <-- 우리 팀 핀 번호로 바꿀 것
```

**교사가 미리 만들어 본 결과 (PC에서 검증, 실물 확인 대기)**

**체크섬 비교 — 3만 회씩 시험**

| 방식 | 1비트 오류 | 2비트 오류 | 3비트 오류 |
|---|---|---|---|
| XOR | 100 % | **88.2 %** | 100 % |
| 덧셈 | 100 % | 94.4 % | 99.1 % |
| **CRC-8** | **100 %** | **100 %** | **100 %** |

XOR은 같은 비트 위치가 짝수 번 뒤집히면 값이 그대로라 못 잡는다. **CRC-8을 쓴다.**

**통신 상태별 (각 500패킷)**

| 상태 | 수신 | 유실률 | 체크섬으로 걸러냄 |
|---|---|---|---|
| 깨끗한 선 | 500 | 0 % | 0 |
| 유실 5 % | 476 | 4.8 % | 0 |
| 잡음 섞임 | 500 | 0 % | 0 |
| 바이트 손상 3 % | 488 | 2.4 % | 11 |

**긴급 정지 — 이게 제일 중요하다**

115200 bps에서 1바이트 = 86.8 us. 영상 8 KB는 **694 ms**가 걸린다.

| | 정지 명령이 나가기까지 | 0.25 m/s에서 진행 |
|---|---|---|
| 영상을 통째로 큐에 넣음 | 595 ms | **14.9 cm** |
| **256바이트씩 조각냄** | **11.6 ms** | **0.29 cm** |

**우선순위만 매겨서는 부족하다.** 이미 보내기 시작한 덩어리는 중간에 못 자르기 때문이다.
큰 것을 조각내야 사이에 끼어들 수 있다.

정지 여유가 20 cm인데 14.9 cm를 밀리면 사실상 못 선다.

**통신 속도** — 시리얼은 **115200**으로 통일한다. 9600은 영상이나 잦은 센서 전송에 느리다.
보내는 쪽과 받는 쪽의 값이 반드시 같아야 한다. 이 값은 팀마다 바꾸지 않는다.
아두이노 예제 대부분이 9600으로 되어 있으니, 코드를 쓸 때마다 아래 줄을 확인한다.

```
void setup() {
  Serial.begin(115200);   // 우리 프로젝트 표준. 9600으로 쓰지 않는다
  pinMode(trigPin, OUTPUT);
  pinMode(echoPin, INPUT);
}
```

**패킷 포맷 예시**

    AA 55 | TYPE | LEN | SEQ | PAYLOAD... | CRC8
     헤더    종류   길이  순번    내용        검사합

    TYPE  0x01 센서값 / 0x02 주행명령 / 0x03 긴급정지 / 0x04 응답 / 0x05 주행
    센서 내용 12바이트 — 시각(4) 앞거리(2) 조도좌(2) 조도우(2) 속도(2)
    센서 패킷 전체 = 18바이트
    주행 내용  4바이트 — 조향(2) 속도배율(1) 깃발(1)   ← 파이 → 아두이노
    주행 패킷 전체 = 10바이트

**0x05 주행 패킷을 왜 따로 두는가 (라즈베리파이 → 아두이노)**

P0 표준규격에서 **차선 유지는 조도 센서(아두이노), 인식은 카메라(파이)** 로 나누기로 확정했다.
파이가 모터값을 직접 보내면 파이가 멈추는 순간 차도 멈춘다.
**속도 배율만** 보내면 파이가 죽어도 아두이노는 조도 센서로 계속 달린다.
아두이노는 500 ms 동안 이 패킷이 안 오면 배율을 1.0 으로 되돌리고 혼자 간다.
("카메라가 실패하면 조도 주행은 계속된다" — P0)

깃발 비트 — 0x01 조향까지 카메라 값 사용 · 0x02 빨간불 · 0x04 감속표지

- 헤더 AA 55 는 패킷이 시작되는 지점을 알린다. 없으면 어디서부터 읽어야 할지 알 수 없다
- SEQ 순번은 유실률을 재려면 반드시 필요하다. 빠진 번호가 곧 유실이다
- CKSUM 은 CRC-8(Dallas/Maxim)이다. XOR 로 시작했다가 2비트 오류의 12%를 놓쳐서 바꿨다
- 🔴 LEN 을 그대로 믿으면 안 된다. 잡음 한 바이트가 길이 자리에 들어와 255가 되면
  `2+3+255+1 = 261` 인데 uint8_t 로는 5로 돌아버려 "다 받았다"고 착각하고
  32바이트 버퍼를 258바이트 읽는다. 받기 전에 LEN 이 버퍼에 들어가는지 먼저 본다

**센서 값 안정화** — 초음파는 다섯 번 재서 가운데 값을 쓴다. 평균은 크게 튄 값 하나에 통째로 끌려간다.

**지연 측정** — 보내는 패킷 안에 보낸 시각을 넣고 받은 시각과 빼면 편도 지연이 나온다. 명령을 보낸 시각과 차가 실제로 멈춘 시각의 차이가 학생이 체감하는 지연이다.

**유실률** — (기대한 순번 개수 빼기 실제로 받은 개수) 나누기 기대한 순번 개수.

**우선순위** — 영상과 명령을 같은 줄에 넣으면 영상 뒤에 정지 명령이 줄을 선다. 명령은 별도 경로로 보내거나 보내기 전에 앞으로 끼워 넣는다.

**라즈베리파이와 아두이노를 잇는다 — 두뇌와 팔다리**

이 프로젝트의 통신은 PC↔아두이노가 아니라 **파이↔아두이노**다.

    카메라 → 라즈베리파이 (조향 판단) ──시리얼──→ 아두이노 (모터·센서)
                  두뇌                              팔다리

파이가 조향을 정하고, 그 값을 아두이노에 보낸다. 아두이노가 모터를 돌린다.
**패킷 포맷·CRC-8·긴급정지 우선순위·지연 측정이 전부 그대로 쓰인다.**
보내는 쪽이 PC 에서 파이로 바뀌었을 뿐이다.

**연결 방법**

USB 케이블 하나면 된다. 파이의 USB 포트와 아두이노를 잇는다.

| 항목 | 값 |
|---|---|
| 연결 | **USB A-B 케이블** (아두이노 우노 기준) |
| 파이에서 보이는 이름 | `/dev/ttyACM0` (우노) 또는 `/dev/ttyUSB0` (나노 호환보드) |
| 통신 속도 | **115200** — 양쪽이 같아야 한다 |
| 파이쪽 라이브러리 | `pyserial` (`pip install pyserial`) |

GPIO 핀으로 직접 잇는 방법도 있지만 USB 가 낫다.
**파이는 3.3 V, 아두이노는 5 V 라 핀을 바로 이으면 파이가 상한다.**
USB 는 그 문제가 없다.

**파이에서 조향값 보내기**

조향은 −1 ~ +1 로 나오므로, 실차 모터 값으로 바꿔 패킷에 싣는다.

    import serial
    ser = serial.Serial("/dev/ttyACM0", 115200, timeout=0.1)

    def send_steer(steer, base=90):
        left  = int(base - steer * base)
        right = int(base + steer * base)
        payload = bytes([left & 0xFF, right & 0xFF])
        pkt = build_packet(TYPE_MOTOR, payload)   # 앞에서 만든 함수
        ser.write(pkt)

`build_packet` 은 이미 만든 것을 그대로 쓴다.
헤더 `AA 55`, TYPE, LEN, SEQ, PAYLOAD, CRC-8 순서다.

**전원을 같이 쓰지 마라**

USB 로 아두이노에 전원이 가지만, **모터 전원은 반드시 따로** 둔다.
모터가 돌 때 전압이 출렁여 파이까지 재부팅된다.

    18650 2개(7.4V) → 모터 드라이버 → 모터
                    → UBEC 5V/3A  → 라즈베리파이

전압 강하 계산이다. 파이 최대 2.0 A + 모터 최대 1.4 A = 3.4 A,
내부저항 0.10 옴이면 강하는 **0.34 V**. 7.4 → 7.06 V 로 UBEC 입력에 여유가 있다.

**지연을 재라 — 어디가 느린지 나눠서**

조향 명령이 늦으면 차가 늦게 선다. 전체 지연을 셋으로 나눠 각각 잰다.

| 구간 | 실측·목표 |
|---|---|
| 파이 추론 | 초당 1,177장 예상 → **1 ms 미만** |
| 시리얼 전송 | 115200 에 15바이트면 **약 1.3 ms** |
| 아두이노 처리·모터 반응 | 나머지 |

한쪽만 재면 어디가 느린지 모른다. **파이에서 보낸 시각을 패킷에 실어 보내고,
아두이노가 응답에 그대로 되돌려 주면** 왕복 시간을 잴 수 있다.

### 교사 실차 경험의 적용 범위

2026년 10월 교사 시제품의 관찰을 익명화한 진단 사례다. 학생 팀의 성공이나 모든 장비의 표준값을 뜻하지 않는다. 수업 표준과 승인된 팀 규격을 보존하고, 완성본 소스·모델·교사 원본 기록은 공개하지 않는다.

### 교사 실차 사례 — 통신 응답과 실제 바퀴 동작을 구분한다.

교사 실차에서 명령 수신 확인은 나왔지만 바퀴가 움직이지 않은 경우가 있었다. 응답은 명령 수신의 근거이며 모터 전원·접지면에서의 출발·좌우 회전 방향까지 증명하지 않는다. 이미 정상 동작을 확인한 검사를 반복하기보다 마지막 성공 때와 현재의 전원·명령·환경 차이 한 가지를 확인한다. 준비 단계의 모터·센서 동작 자체를 새 평가 항목으로 삼지 않는다.

<!-- FIELD_CASE: startup_pwm | PWM|한쪽|출발|힘이|배터리 -->
### 교사 실차 사례 — 출발 가능한 출력은 장비별로 확인한다.

낮은 출력에서는 한쪽 바퀴만 출발하고 다른 출력에서는 네 바퀴가 출발한 교사 사례가 있다. 모든 팀에 같은 출발값이 맞는다는 근거는 아니다. 배터리 문제로 단정하거나 무조건 출력을 올리지 말고 이미 확보한 명령·전원·실제 동작을 대조한다. 학생에게 주행을 요청할 때는 모터 전원 상태, 제한 시간과 정지 방법을 분명히 안내한다.

### 교사 실차 사례 — 펌웨어와 표준 규격을 혼용하지 않는다.

교사 진단 장치의 문자 명령·수신 확인 방식은 수업 표준의 바이너리 CRC 패킷과 같은 규격이 아니다. 실행 버전과 팀 규격을 확인하지 않고 서로의 명령·핀 배치를 섞거나 펌웨어를 다시 올리게 하지 않는다. 보드 인쇄 표기, 실드 단자와 연결된 MCU 핀은 구별한다. 실제 결선 변경은 키트를 담당하는 교사와 확인한다.

## 5. 자주 나오는 질문과 되물어야 할 것

| 학생이 이렇게 물으면 | 이렇게 되묻는다 |
|---|---|
| 통신이 안 돼요 | 포트가 열렸어? 양쪽 통신 속도가 같아? 시리얼 모니터를 켜 둔 채로 다른 프로그램에서 열려고 한 건 아니야? |
| 값이 깨져서 와요 | 헤더랑 체크섬 넣었어? 한 패킷 길이가 고정이야, 가변이야? |
| 늦게 멈춰요 | 명령 보낸 시각이랑 차가 멈춘 시각 차이가 몇 밀리초야? 재 봤어? |
| 모터가 안 돌아요 | 배선까지 끝났어? 코드는 올렸어? 시리얼에 뭐가 찍혀? |
| 값이 튀어요 | 몇 번 재서 쓰고 있어? 평균 쓰고 있어, 가운데 값 쓰고 있어? |
| 최적화를 어떻게 해요? | 지금 지연이 몇 밀리초고 유실률이 몇 퍼센트야? 먼저 재고 오자 |
| 어디부터 해야 해요? | 지금 차가 움직이기는 해? 센서 값은 찍혀? 둘 중 어디서 막혔어? |
| 체크섬 뭘로 해요? | CRC-8이야. XOR은 2비트 오류의 12%를 놓쳐서 안 써 |
| 정지 명령이 늦게 가요 | 영상이랑 같은 줄에 넣었어? 큰 데이터를 256바이트씩 조각냈어? |
| 유실률을 어떻게 재요? | 패킷에 순번 넣었어? 없으면 몇 개 사라졌는지 알 방법이 없어 |

## 6. 다른 과목과의 접점

**받는 것**
  - 센서 마운트 치수·장착 규격 ← 3D 프린터용 제품 제작
  - 학습된 인식 모델 ← 인공지능 모델링
**주는 것**
  - 실차 주행 로그 → 게임 프로그래밍

범위 밖 질문이 오면 담당 과목을 알려 주고 그 팀에 요청하라고 안내한다.
