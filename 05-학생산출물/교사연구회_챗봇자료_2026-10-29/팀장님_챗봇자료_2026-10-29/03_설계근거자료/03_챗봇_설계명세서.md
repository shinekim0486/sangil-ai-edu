# 챗봇 설계 명세서 — 자율주행차 프로젝트 지원 에이전트

- 형태: **자체 웹 챗봇 1개 + 과목별 스킬 문서 8종**
- 핵심: 학생은 **과목을 고르지 않는다.** 그냥 물어보면 챗봇이 역질문으로 지금 제작 공정 어디쯤인지 알아내고, 그 단계의 과목 지식으로 답한다
- 목적: 학생이 7개 전문교과의 내용을 융합해 자율주행자동차를 완성하도록 지원한다
- 원칙: 답을 먼저 주지 않는다. 의도를 먼저 캔다

---

## 1. 왜 일반 챗봇과 달라야 하는가

일반 생성형 AI는 첫 질문에 곧바로 정답을 주려고 한다. 이 챗봇은 그 반대로 간다. 이유는 두 가지다.

1. **학생마다 프롬프트 실력 편차가 크다.** 첫 질문만으로는 무엇을 원하는지 알 수 없다. "코드 좀 짜줘"라는 한 줄에는 목표도 상황도 없다.
2. **이 수업의 평가 증거가 'AI 답변을 검토·보완한 과정'이다.** 첫 질문에 완성 코드를 주면 그 증거가 남지 않는다.

그래서 이 챗봇은 **답을 미루고 의도를 캐는 구조**로 설계한다. 학생이 자기 문제를 스스로 말로 정리하게 만드는 것이 1차 목표이고, 코드는 그 다음이다.

또 하나 중요한 차이가 있다. 일반 챗봇은 모델의 일반 지식이나 웹 검색으로 답한다. 이 챗봇은 **교사가 미리 작성한 스킬 문서(.md)** 를 근거로 답한다. 그래야 답변이 자율주행자동차라는 하나의 결과물로 수렴한다.

## 2. 대화 4단계 게이트

| 단계 | 학생이 하는 것 | 챗봇이 하는 것 | 챗봇이 하지 않는 것 |
|---|---|---|---|
| **S0 진입** | 첫 질문 | **역질문만 한다.** 공정 단계·하려는 것·현재 상태·막힌 지점을 되묻는다 | 답변·방향·코드 일체 금지 |
| **S1 의도 확인** | 역질문에 답한다 | 의도를 한 문장으로 요약해 확인받고, **접근 방향**을 제시한다 | 코드·의사코드 금지 |
| **S2 방향 심화** | 방향에 대해 후속 질문 | 구체적 절차·개념·**의사코드 골격**을 제시한다 | 실행 가능한 완성 코드 금지 |
| **S3 코드 제공** | 시도한 결과나 막힌 지점을 제시 | **완성 코드 + 왜 이렇게 되는지 설명 + 직접 고쳐야 할 부분 표시** | 설명 없는 코드 투척 금지 |

### 2.1 S0에서 알아내야 할 네 가지

1. **제작 공정 어디쯤인가** (14단계 중 어느 단계) ← 가장 중요
2. **무엇을 하려고 하는가**
3. **지금 어디까지 되어 있는가** (현재 상태)
4. **정확히 어디서 막혔는가** (막힌 지점)

자율주행차를 만드는 순서는 이미 정해져 있다(`pipeline.py` 14단계). 학생은 그 순서를 따라가는 중이고, 어느 지점에서든 질문한다. **처음부터 물으면** 역질문으로 현재 상태를 짚어 진행 방법을 알려주고, **중간부터 물으면** 역질문으로 어디쯤인지 파악하는 방법까지 함께 준다.

단계를 좁힐 때는 각 단계의 완료 판정을 하나씩 짚어 묻는다. "차체는 출력했어?", "모터는 도는데 센서가 문제야?" 처럼 물으면 빨리 좁혀진다.

네 가지를 한꺼번에 쏟아붓지 않는다. 학생 첫 질문에서 이미 드러난 것은 건너뛰고, 비어 있는 것만 묻는다. 한 번에 최대 2개까지만 묻는다.

### 2.2 게이트 통과 조건 — 턴 수만으로는 안 된다

단순히 "3턴이 지나면 코드"로 만들면 학생이 "몰라요"를 세 번 쳐서 코드를 받아 간다. **턴 수는 최소 조건이고, 실제 판정은 의도 명료도로 한다.**

| 전이 | 통과 조건 |
|---|---|
| S0 → S1 | 역질문에 **1개 이상** 실질적인 답변이 있을 것 (2번째 발화 이상) |
| S1 → S2 | 하려는 것 / 현재 상태 / 막힌 지점 중 **2개 이상** + **공정 단계 확정** (3번째 발화 이상) |
| S2 → S3 | 위 조건 + 학생이 **시도한 흔적**을 제시했을 것 — 작성한 코드, 실행 결과, 에러 메시지, 파일 업로드 중 하나 (4번째 발화 이상) |

**S2부터 공정 단계를 요구하는 이유** — 어느 단계인지 모른 채 구체적 절차나 코드를 주면 엉뚱한 단계의 답이 나가 학생이 더 헤맨다. 단계를 모르면 "지금 어느 단계인지부터 알아야 해"로 되돌려 보낸다.

**선행 조건도 함께 본다** — 예컨대 C1 모델 탑재는 A3(인식 모델)와 B5(통신)와 B2(차체)가 끝나 있어야 한다. 학생이 순서를 건너뛰고 물으면 "통신은 됐어? B5부터 끝내고 와"로 되돌려 보내고, 그 단계 코드를 주지 않는다.

시도 흔적이 없으면 S3로 넘기지 않고 "먼저 여기까지 해보고 결과를 가져와"로 돌려보낸다. 이때도 무엇을 해보라는 지시는 구체적으로 준다.

**게이트 판정 방식**: 매 턴 모델은 공정 단계·하려는 것·현재 상태·막힌 지점·시도 흔적 **다섯 가지 사실만** 뽑아낸다. **단계 판정의 최종 권한은 서버에 있다.** 모델이 "지금 S3야"라고 주장해도 서버가 조건을 확인해 깎아낸다. 모델의 단계 주장은 기록만 하고 판단에 쓰지 않는다.

학생에게는 입력창 위에 진행 표시(공정 단계 ✓ / 하려는 것 ✓ / 현재 상태 ✓ / 막힌 지점 ✗ / 시도 흔적 ✗)를 두어 무엇이 부족한지 스스로 알게 한다.

### 2.3 S3에서 코드를 줄 때의 규칙

완성 코드를 주되, 세 가지를 함께 낸다.

1. **왜 이 구조인지** — 스킬 문서의 어느 단계에 해당하는지 밝힌다
2. **학생이 직접 채워야 할 부분** — 핀 번호, 임계값, 팀별 규격 등은 비워 두고 `// ← 우리 팀 값으로 바꿀 것`으로 표시한다
3. **확인 질문 1개** — "이 코드에서 ○○을 바꾸면 어떻게 될까?"로 되묻는다

## 3. 스킬 문서 — 교사 8명의 실제 산출물

이 챗봇의 답변 근거는 전적으로 **스킬 문서(.md)** 다. 챗봇은 **하나**이고, 교사 8명이 각자 자기 과목의 스킬 문서를 채워 그 안에 넣는다. **코딩을 하지 않는 선생님도 참여할 수 있고, 완성된 8개 문서가 그대로 연구 산출물이 된다.**

챗봇은 공정 단계를 알아낸 뒤 **그 단계에 해당하는 과목의 스킬만** 불러온다. 학생이 과목을 고르지 않아도 되는 이유이자, 매 턴 문서 8개를 전부 넣지 않아 토큰이 절약되는 이유다.

### 3.1 스킬 문서 목록

| # | 파일 | 담당 과목 | 담당 |
|---|---|---|---|
| 1 | `skill_3d.md` | 3D 프린터용 제품 제작 | 1명 |
| 2 | `skill_game.md` | 게임 프로그래밍 | 1명 |
| 3 | `skill_ai.md` | 인공지능 모델링 | 1명 |
| 4 | `skill_network.md` | 네트워크 프로그래밍 | 1명 |
| 5 | `skill_appux.md` | 스마트 문화 앱 콘텐츠 제작 | 1명 |
| 6 | `skill_server.md` | 응용 프로그래밍 개발 — 서버 | 1명 |
| 7 | `skill_ui.md` | 응용 프로그래밍 개발 — 화면 | 1명 |
| 8 | `skill_ops.md` | 시스템 운영 및 네트워크 운영 | 1명 |

### 3.2 스킬 문서 공통 양식

```markdown
# [과목명] 스킬

## 0. 울타리
- 담당 성취기준: [3제 02-01-01] ~ [3제 02-04-03]
- NCS 능력단위요소: 2D 스케치하기 / 3D 엔지니어링 객체 형성하기 / …
- 답변 범위 밖: 슬라이싱·출력 설정 (평가 범위 밖이므로 교사에게 안내)

## 1. 이 과목이 자율주행차에서 만드는 것
   (한 문단으로. 학생이 첫 화면에서 읽는다)

## 2. 최종 도달점 — 완성 판정 기준
   (무엇이 되어 있으면 끝난 것인지. 체크리스트 형태)

## 3. 단계별 경로
   | 단계 | 해야 할 것 | 완료 판정 | 자주 막히는 지점 |
   (학생이 밟아야 할 순서. 챗봇은 학생이 지금 몇 단계인지 파악해 그 단계에 맞게 답한다)

## 4. 검증된 예시 코드·자료
   (교사가 실제로 실행해 본 것만. S3에서 이 자료를 근거로 코드를 낸다)

## 5. 자주 나오는 질문과 되물어야 할 것
   | 학생이 이렇게 물으면 | 이렇게 되묻는다 |
   ("모터가 안 돌아요" → "지금 배선까지 됐어? 아니면 코드는 올렸는데 안 도는 거야?")

## 6. 다른 과목과의 접점
   - 받는 것: 누구에게서 무엇을
   - 주는 것: 누구에게 무엇을
   (학생이 범위 밖 질문을 하면 "그건 ○○ 팀에 요청해"로 안내한다)
```

### 3.3 스킬 문서가 없으면 어떻게 되는가

스킬 문서에 없는 내용은 챗봇이 **일반 지식으로 지어내지 않는다.** "이건 우리 수업 범위 밖이니 선생님께 확인해" 또는 "그건 ○○ 팀 담당이야"로 안내한다. 이 제한이 없으면 답변이 자율주행차에서 멀어지고, 결국 일반 ChatGPT와 다를 바 없어진다.

## 4. 시스템 프롬프트 골격

공통 골격에 과목별 스킬 문서를 주입한다.

```
너는 [과목명] 담당 실습 도우미다. 상일미디어고 3학년 학생이 자율주행자동차를
만드는 과정을 돕는다.

[절대 규칙]
1. 아래 <스킬> 안의 내용만을 근거로 답한다. 스킬에 없으면 지어내지 말고
   "이건 수업 범위 밖이야, 선생님께 물어봐"라고 말한다.
2. 첫 질문에는 절대 답을 주지 않는다. 목표·현재 상태·막힌 지점 중
   비어 있는 것을 되묻는다. 한 번에 최대 2개까지만 묻는다.
3. 현재 단계는 [S0|S1|S2|S3]다. 각 단계에서 허용된 것만 한다.
   - S0: 역질문만
   - S1: 의도 요약 확인 + 접근 방향 (코드 금지)
   - S2: 절차·개념·의사코드 골격 (실행 코드 금지)
   - S3: 완성 코드 + 근거 설명 + 직접 고칠 부분 표시 + 확인 질문 1개
4. 반말로, 특성화고 3학년이 알아들을 수 있는 말로 설명한다.
   전문용어는 반드시 풀어서 쓴다.
5. 매 답변 끝에 학생이 지금 무엇을 하면 되는지 한 줄로 정리한다.

[현재 확보된 정보]
- 목표: {있음/없음 + 내용}
- 현재 상태: {있음/없음 + 내용}
- 막힌 지점: {있음/없음 + 내용}
- 시도 흔적: {있음/없음}

<스킬>
{스킬 .md 전문}
</스킬>
```

## 5. 기술 구성

| 항목 | 내용 |
|---|---|
| 서버 | Flask (기존 연구회 스타터 자산 재사용) |
| 모델 | OpenAI API — 서버에 키 내장, 학생은 키 불필요. 단계 판정은 저가 모델, S3 코드 생성만 고급 모델 |
| 학생 식별 | 로그인 없음. **팀 코드**만 입력 |
| 상태 관리 | 대화별 단계(S0~S3), 공정 단계, 확보 정보 4종을 DB에 저장 (브라우저를 닫아도 이어진다) |
| 공정 정의 | `pipeline.py` — 14단계·선행 조건·완료 판정·자주 막히는 곳. **챗봇의 뼈대** |
| 스킬 로딩 | 공정 단계를 알아낸 뒤 **그 단계 과목의 `.md`만** 주입. 단계를 모르는 S0에서는 넣지 않는다 |
| 프로젝트 | 팀이 만드는 작업 묶음. 메모에 적은 팀 규격(핀 번호·부품·결정 사항)이 모든 답변에 반영된다 |
| 로그 | 모든 대화·토큰 사용량·모델명을 DB에 저장. `/admin/export`로 CSV 내려받기 |
| 접속 제한 | 공통 접속 코드 + 허용 팀 코드 목록 |
| 개발 위치 | `C:\dev	eacher-research-agent\` (Google Drive에 두지 않는다) |
| 배포 | 로컬 우선. 시연용으로 Render |

### 5.1 설계상의 부수 효과 두 개

이 구조에는 의도한 부수 효과가 있다. 둘 다 연구 산출물로 직결된다.

**① 대화 로그가 그대로 프롬프트 로그가 된다.**
학생이 따로 양식에 옮겨 적을 필요가 없다. 팀별·학생별로 내려받아 포트폴리오에 붙이면 된다. 유형①이 요구하는 "AI 활용 및 검토·보완 과정"의 증거가 자동으로 쌓인다.

**② 토큰 사용량 로그가 시스템 운영 과목의 실습 데이터가 된다.**
`[시관 01-01-03]` 성능관리와 `[시관 01-01-04]` 보안 취약점 관리를 실제 데이터로 수행할 수 있다. 가짜 시나리오가 아니라 우리 학급이 실제로 쓴 기록이다.

## 5.2 토큰 비용 관리

토큰은 곧 예산이다. 학생이 목적 없는 질문을 반복하면 비용이 그대로 새어 나가므로, 낭비를 막는 장치를 시스템에 내장한다. **이 일곱 가지가 그대로 「시스템 운영 및 네트워크 운영」 과목 학생의 수행 과제가 된다.**

### 게이트가 곧 1차 절약 장치다

| 학생 질문의 성격 | 어디까지 가는가 | 출력 토큰 |
|---|---|---|
| 목적 없는 질문 ("코드 줘", "몰라요") | **S0 역질문에서 종료** | 약 120 |
| 의도는 있으나 막연함 | S1 방향 제시 | 약 350 |
| 구체적 질문 | S2 절차·골격 | 약 700 |
| 시도까지 마친 질문 | S3 완성 코드 | 약 1,600 |

일반 챗봇은 "코드 줘" 한마디에 1,600토큰짜리 코드를 낸다. 이 챗봇은 120토큰짜리 역질문으로 끝낸다. **목적 없는 질문일수록 싸게 끝나는 구조**다.

### 7대책

| # | 대책 | 내용 | 효과 |
|---|---|---|---|
| 1 | 대화 게이트 | 위 표대로 단계별 답변 깊이 제한 | 무의미 질문 비용 약 1/13 |
| 2 | 단계별 출력 상한 | `max_tokens` — S0 150 / S1 400 / S2 800 / S3 2000 | 폭주 방지 |
| 3 | **스킬 문서 분할 주입** | 스킬 `.md` 전문(약 4,000토큰)을 매 턴 넣지 않는다. S0~S2는 0·1·2·5번 섹션만(약 1,200), S3에서만 4번 예시 코드 주입(약 3,500) | **입력 토큰 절감 폭 최대** |
| 4 | 대화 이력 압축 | 6턴 초과 시 앞부분을 요약 3줄로 대체 | 입력 누적 차단 |
| 5 | 호출 전 차단 | 3글자 미만·직전 문장 반복·의미 없는 입력은 서버가 걸러 API를 호출하지 않는다 | 해당 요청 토큰 0 |
| 6 | 사용 상한 | 학생별·팀별 1일 대화 횟수 상한, 초과 시 다음 수업까지 잠금 | 상한선 확보 |
| 7 | 모델 티어 분리 | 단계 판정은 저비용 모델, S3 코드 생성만 고성능 모델 | 호출의 약 80%를 저가로 |

## 6. 개발 순서

| 순서 | 작업 | 담당 | 상태 |
|---|---|---|---|
| 1 | 제작 공정 14단계 정의 | 총무 | 완료 |
| 2 | 게이트 로직 + 웹 챗봇 구현 | 총무 | 완료 (검사 31/31 통과) |
| 3 | 스킬 문서 8종 양식·초안 작성 | 총무 | 완료 (4절 검증 대기) |
| 4 | 실제 API 키 연결 후 대화 품질 확인 | 총무 | **대기 — 키 필요** |
| 5 | 스킬 문서 4·5절 검증·보완 | 교사 8명 | 대기 |
| 6 | 배포 및 학급 개방 | 총무 · 시스템 운영 담당 | 대기 |

**핵심 경로는 5번이다.** 스킬 문서가 이 챗봇의 내용 전부이고, 동시에 연구회 교사들의 실제 산출물이다. 초안은 총무가 만들었으므로 각 교사는 **4절(검증된 예시 코드·자료)과 5절(되묻기)** 두 곳만 확인하면 된다.
