# packet_format_v1.md — AUTO-NET LAB 1차시 산출물 (TICKET-01)

> 작성자: 학생 코드 30106 / 팀: CAR2 / 날짜: 2026-09-22

## 1. 패킷 구조 (6개 필드)

| 필드 | 바이트 크기 | 역할 | 이번 설계 값 |
|---|---|---|---|
| SOF (Start of Frame) | 2 bytes | 패킷 시작을 알리는 고정 신호 | AA 55 |
| TYPE | 1 byte | 명령의 종류 | 0x03 (긴급 정지) |
| LENGTH | 2 bytes | PAYLOAD의 바이트 수 (전체 길이 아님) | 00 01 |
| SEQ | 4 bytes | 순서 번호 (전송 시각 아님) | 00 00 00 01 |
| PAYLOAD | LENGTH가 가리키는 만큼 | 실제 명령 데이터 | 32 |
| CHECKSUM | 1 byte | 오류 검사값 (CRC-8 또는 XOR 비교) | 수업 중 계산·확인 |

## 2. TYPE 정의

| TYPE 값 | 의미 | 비고 |
|---|---|---|
| 0x01 | 주행 명령 | 속도·방향 값을 PAYLOAD에 포함 |
| 0x02 | 상태 요청 | 응답으로 상태 패킷을 받음 |
| 0x03 | 긴급 정지 | 안전 규칙과 직결되는 핵심 명령 |

## 3. 설계 근거 (한 줄씩)

- LENGTH를 PAYLOAD만의 길이로 정한 이유: 네트워크 구성도를 그려보니 PAYLOAD를 최소화하면 전송이 빨라질 것 같아 1바이트로 줄여봤는데, 명령 종류가 늘면 부족할 수 있어 재검토가 필요합니다.
- SEQ를 순서 번호로 쓰기로 한 이유 (시각이 아닌 이유): 수신 측에서 순서를 재구성하려면 시각이 아니라 증가 번호가 필요합니다.
- PAYLOAD에 넣은 값과 그 의미: 정지 명령 코드.

## 4. CRC-8 vs XOR 비교 (판단 4칸)

| 비교 항목 | CRC-8 | XOR |
|---|---|---|
| 잡을 수 있는 오류 | 연속·다중 비트 오류까지 비교적 잘 잡음 | 같은 자리 비트가 두 번 바뀌면 못 잡음 |
| 계산 비용 | XOR보다 다소 큼 | 매우 단순, 계산 빠름 |
| 우리 팀 선택 | ☑ | ☐ |
| 선택 이유 (한 줄) | XOR은 같은 자리가 두 번 바뀌면 못 잡는 한계가 있어 CRC-8 다항식 쪽을 선택 |

> 1차시에는 CRC-8과 XOR을 비교합니다. 최종 CHECKSUM 방식은 3차시 팀 투표로 CRC-8을 확정합니다.

## 5. 주행·긴급정지 명령 전송 확인

| 전송 명령 | TYPE | 전송 순서(SEQ) | 전송 확인 방법 | 결과 |
|---|---|---|---|---|

| 긴급 정지 명령 | 0x03 | 00 00 00 02 | AUTO-NET LAB 수업용 시뮬레이션 | ☑ 성공 ☐ 실패 |

## 6. 인계 메모 (다음 차시로 넘길 내용)

- 오늘 확정한 패킷 형식에서 아직 확신이 서지 않는 부분: TYPE 값으로 필터링하는 것과 실제 하드웨어 배치가 어떻게 연결되는지.
- 2차시(지연 측정)에서 꼭 확인하고 싶은 것: LENGTH를 줄였을 때 실제 전송 속도 차이를 측정해보고 싶습니다.
- 팀 내 역할 분담 상태: 제가 구성도 그리기, 짝이 필드값 입력을 맡았습니다.
