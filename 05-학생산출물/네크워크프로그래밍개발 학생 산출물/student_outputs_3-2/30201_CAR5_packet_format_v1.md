# packet_format_v1.md — AUTO-NET LAB 1차시 산출물 (TICKET-01)  
  
> 작성자: 학생 코드 30201 / 팀: CAR5 / 날짜: 2026-09-22  
  
## 1. 패킷 구조 (6개 필드)  
  
| 필드 | 바이트 크기 | 역할 | 이번 설계 값 |  
|---|---|---|---|  
| SOF (Start of Frame) | 2 bytes | 패킷 시작을 알리는 고정 신호 | AA 55 |  
| TYPE | 1 byte | 명령의 종류 | 0x03 (긴급 정지) |  
| LENGTH | 2 bytes | PAYLOAD의 바이트 수 (전체 길이 아님) | 00 02 |  
| SEQ | 4 bytes | 순서 번호 (전송 시각 아님) | 00 00 00 01 |  
| PAYLOAD | LENGTH가 가리키는 만큼 | 실제 명령 데이터 | 32 00 |  
| CHECKSUM | 1 byte | 오류 검사값 (CRC-8 또는 XOR 비교) | 수업 중 계산·확인 |  
  
## 2. TYPE 정의  
  
| TYPE 값 | 의미 | 비고 |  
|---|---|---|  
| 0x01 | 주행 명령 | 속도·방향 값을 PAYLOAD에 포함 |  
| 0x02 | 상태 요청 | 응답으로 상태 패킷을 받음 |  
| 0x03 | 긴급 정지 | 안전 규칙과 직결되는 핵심 명령 |  
  
## 3. 설계 근거 (한 줄씩)  
  
- LENGTH를 PAYLOAD만의 길이로 정한 이유: 참조카드에서 LENGTH가 PAYLOAD 길이라고 색으로 표시해둬서 그대로 적었어요.  
- SEQ를 순서 번호로 쓰기로 한 이유 (시각이 아닌 이유): SOF 다음 TYPE, 그다음 LENGTH… 색칠하면서 순서대로 익혔어요. SEQ는 순서 번호라고 배웠어요.  
- PAYLOAD에 넣은 값과 그 의미: 정지 명령 값이요.  
  
## 4. CRC-8 vs XOR 비교 (판단 4칸)  
  
| 비교 항목 | CRC-8 | XOR |  
|---|---|---|  
| 잡을 수 있는 오류 | 연속·다중 비트 오류까지 비교적 잘 잡음 | 같은 자리 비트가 두 번 바뀌면 못 잡음 |  
| 계산 비용 | XOR보다 다소 큼 | 매우 단순, 계산 빠름 |  
| 우리 팀 선택 | ☐ | ☑ |  
| 선택 이유 (한 줄) | 색으로 구분한 참조카드에서 더 간단해 보이는 쪽 |  
  
> 1차시에는 CRC-8과 XOR을 비교합니다. 최종 CHECKSUM 방식은 3차시 팀 투표로 CRC-8을 확정합니다.

## 6. 인계 메모 (다음 차시로 넘길 내용)  
  
- 오늘 확정한 패킷 형식에서 아직 확신이 서지 않는 부분: 16진수 창이 빽빽해서 아직 필드 경계를 한눈에 못 찾을 때가 있어요.  
- 2차시(지연 측정)에서 꼭 확인하고 싶은 것: 참조카드를 2차시에도 계속 쓸 수 있는지 궁금해요.  
- 팀 내 역할 분담 상태: 저는 시각자료 색칠·정리를 맡았어요.
