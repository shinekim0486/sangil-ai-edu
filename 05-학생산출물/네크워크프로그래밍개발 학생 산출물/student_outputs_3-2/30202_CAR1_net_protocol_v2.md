## 5. 프로토콜 v2 명세 (게임팀·서버팀 구현용) 🟦  
  
| 항목 | v1 (1차시) | v2 (이번 차시) |  
|---|---|---|  
| 패킷 구조 | SOF·TYPE·LENGTH·SEQ·PAYLOAD·CHECKSUM | 유지 |  
| TYPE 03 (긴급 정지) 처리 | 도착 순서대로 처리 | TYPE 03을 최우선 큐로 먼저 전송 (일반 센서 데이터는 그 뒤) |  
| 대용량 데이터(영상 등) 처리 | 통째 전송 | 통째 전송 유지 (전략 B 팀 결과 참고) |  
| 유실 처리 | 미정 | SEQ 번호가 건너뛰면 유실로 기록, 평균에서 제외 |  
| CHECKSUM 방식 | CRC-8 / XOR 비교 중 | 1차시 선택 유지 (최종 확정은 3차시) |  
  
## 6. 45초 발표 요약과 3문장 회고 (S#14)  
  
**발표 문장** 🟦  
> 저희 팀은 같은 조건에서 RTT를 기준 95.1ms, 전략 적용 후 61ms로 관찰했습니다. 유실률은 10%에서 10%로 변했습니다. 결과는 개선 (정지 명령 기준)입니다. 편도 제어 지연 자료는 없음이며, 주행거리 환산은 하지 않음으로 적었습니다. 한계는 10회만 측정해 6회차처럼 튀는 값의 원인을 확정하지 못함, 센서 RTT는 오히려 늘어남입니다.  
  
**3문장 회고** 🟩  
- 처음 생각한 것: SEQ에 시각을 적으면 된다고 생각했고, RTT도 시각 차이만 보면 된다고 여겼습니다.  
- 본 증거: 시각만 보면 몇 번째 패킷이 빠졌는지 알 수 없었고, SEQ로 4번 유실을 찾았습니다.  
- 바뀐 판단: 시각은 지연을 재는 데, SEQ는 순서와 유실을 찾는 데 씁니다.
